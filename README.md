# برف‌کو / SnowF 🏔️

**دستیار تصمیم اسکی — «امروز کجا بریم؟»**

برف‌کو یک ابزار تصمیم‌گیری برای اسکی‌بازان ایران است که با استفاده از داده‌های رایگان هواشناسی، چهار پیست اصلی (توچال، دیزین، دربندسر، شمشک) را مقایسه می‌کند و در چند ثانیه جواب این سؤالات را می‌دهد:

-  امروز کدام پیست بهتر است؟
- 📅 چه روزی برای اسکی بهتر است؟
- 🏔️ در کدام ارتفاع (پایین / میانی / قله) شرایط بهتر است؟
- ⏰ چه ساعتی بهترین زمان رفتن است؟
- ❄️ کیفیت احتمالی برف چگونه است؟
- ⏳ اگر فقط یک روز فرصت داری، چه؟

> ⚠️ **سلب مسئولیت ایمنی:** همه‌ی شاخص‌های این سایت (کیفیت، ایمنی، ریسک جوی کوهستان) **برآوردهای خودکار** از روی داده‌های هواشناسی هستند و **جایگزین گزارش رسمی بهمن، اطلاعیه پیست، یا توصیه کارشناسان کوهستان نیستند.** هیچ ادعایی از نوع «سطح بهمن EAWS X» مطرح نمی‌شود.

## دقت داده: شبکه‌ی مدل و ارتفاع (مهم)

این مهم‌ترین محدودیت فنی پروژه است و کل طراحی حول آن شکل گرفته:

**۱) شبکه‌ی مدل.** Open-Meteo خروجی مدل را روی شبکه‌ای حدود **۱۱ کیلومتری** می‌دهد. یک پیست اسکی کمتر از ۲ کیلومتر عرض دارد، بنابراین هر سه ایستگاه یک پیست معمولاً داخل **یک سلول شبکه** می‌افتند و در نتیجه:

- باد، گاست، ابر، بارش و دید آن‌ها **یکسان** است (یک عدد، نه سه);
- فقط **دما** به‌ازای ارتفاع تفکیک می‌شود، چون Open-Meteo دما را به ارتفاع DEM نقطه‌ی درخواستی تصحیح می‌کند.

پروژه این واقعیت را **پنهان نمی‌کند**: ایستگاه‌هایی که روی یک سلول می‌افتند شناسایی می‌شوند (`sharedGridCell()`)، در رابط کاربری با هشدار صریح نمایش داده می‌شوند و «پایه توصیه» (confidence) آن‌ها ۸ واحد کم می‌شود.

**۲) تصحیح ارتفاع.** مختصات هر ایستگاه طوری انتخاب شده که ارتفاع DEM آن با ارتفاع رسمی ایستگاه بخواند (خطای فعلی ≤ ۷۵ متر). باقی‌مانده‌ی اختلاف در `js/weather.js → heightCorrection()` با نرخ گرادیان استاندارد هوا **۶٫۵ درجه بر کیلومتر** اصلاح می‌شود:

```
ΔT = -(ارتفاع ایستگاه − ارتفاع DEM) × 0.0065
```

این تصحیح فقط روی متغیرهای ترمودینامیکی (`temperature_2m`، `apparent_temperature`، `dew_point_2m`) اعمال می‌شود — نه روی باد، بارش، ابر، دید یا عمق برف. صحت این نرخ به‌صورت تجربی تأیید شده: دو نقطه در یک سلول شبکه با اختلاف ارتفاع ۱۵۱ متر، اختلاف دمای ۱٫۰ درجه گزارش کردند (معادل ۶٫۶ درجه بر کیلومتر).

## منطق امتیازدهی (خلاصه)

کامل و با اعداد در [`js/config.js`](js/config.js). اصول:

1. **بدون double-counting:** باد با «باد مؤثر = max(sustained, gust×0.65)» فقط یک‌بار؛ برف تازه ≠ عمق برف ≠ سطح برف (سه مفهوم جدا)؛ CAPE+LI یک عامل ترکیبی.
2. **ایمنی مستقل است و رأی را درِگذاری می‌کند:** ایمنی < ۴۰ → AVOID؛ < ۶۵ → حداکثر CAUTION؛ stopهای سخت (گاست > ۸۵، دید < ۰.۵) همیشه AVOID.
3. **کفِ بدترین ایستگاه:** اگر ایمنیِ یکی از ایستگاه‌ها < ۳۵ باشد → AVOID؛ اگر < ۵۵ باشد → حداکثر CAUTION. این کف مستقل از میانگین وزنی پیست است، پس یک ایستگاه خطرناک هرگز با دو ایستگاه آرام پنهان نمی‌شود.
4. **کالیبراسیون ایمنی:** یک عامل جدی ≈ ‎-۴۰ (ایمنی ۶۰ ← احتیاط)، دو عامل جدی ← پرهیز.
5. **داده ناقص = سقف:** نبود داده باد/دید ایمنی را بالا نگه نمی‌دارد (سقف ۸۵/۹۰) و اطمینان را کاهش می‌دهد.
6. **ریسک جوی فقط سقف می‌زند** (نه کسر دوباره) و هرگز «بستن پیست» را از روی CAPE اعلام نمی‌کند.
7. **یک حالت واحد** (پروفایل‌های کاربری حذف شده‌اند): یک درِ ثابت و مستند — «برو» یعنی ایمنی ≥ ۶۵ **و** کیفیت ≥ ۵۰ و عمق ≥ ۸ سانتی‌متر؛ ایمنی هرگز با کیفیت میانگین نمی‌شود.
8. **گیت عمق برف روی بهترین ایستگاه** (نه فقط قله): قله‌ی بادخورده نباید پیستی را که ایستگاه میانی‌اش ۶۰ سانتی‌متر برف دارد محکوم کند.

## منبع داده

[Open-Meteo](https://open-meteo.com) — رایگان، بدون کلید API. فقط متغیرهایی که endpoint رایگان پشتیبانی می‌کند (لیست در `js/api.js`).

**محدودیت‌های علمی (راست‌گو):**
- خروجی مدل روی شبکه‌ی ~۱۱ کیلومتری است؛ باد/بارش/دید بین ایستگاه‌های یک پیست تفکیک نمی‌شود (فقط دما تفکیک می‌شود).
- `snow_depth` مدل NWP است و پوشش واقعی برف پیست را نمی‌سنجد (به‌خصوص پاییز/بهار).
- `freezing_level_height` در ارتفاع‌های ۲۵۰۰+ متر از نظر مدل بی‌دقت‌تر است.
- باران یخ‌زده **با قاعده‌ی ساده تخمین** می‌زند (API این متغیر را ندارد) — همیشه با برچسب «احتمال/برآورد».
- پیش‌بینی ۶-۱۶ روزه ذاتاً کم‌دقت است — Confidence با افق کاهش می‌یابد.
- داده‌ها برای ایستگاه‌های جغرافیایی پیست است، نه تله‌کابین/پایه‌ی رسمی.

## GitHub Pages

کار می‌کند — همه‌ی مسیرها نسبی‌اند و workflow موجود (`.github/workflows/static.yml`) کل ریپو را deploy می‌کند.

> سرویس‌ورکر با الگوی **stale-while-revalidate** کار می‌کند: نسخه‌ی جدید در **بازدید بعدی** کاربران اعمال می‌شود و نیازی به بالا بردن دستی نسخه نیست. درخواست‌هایی که `cache: 'no-cache'` دارند (مثل `data/resorts.json`) همیشه network-first هستند تا کش قدیمی جای داده‌ی تازه را نگیرد.
>
> **پوسته‌ی HTML استثناست:** درخواست‌های ناوبری (`mode: 'navigate'`) همیشه **network-first** هستند (با fallback به کش برای حالت آفلاین). اگر پوسته هم stale-while-revalidate بود، هر تغییر در markup یک بازدید عقب می‌ماند — که برای سایتی با HTML کوچک ضرری ندارد.

## نسخه‌بندی

`js/config.js → APP.version` تنها منبع حقیقت است. `package.json` باید با آن یکی باشد (در CI بررسی می‌شود). نسخه در پاورقی سایت به‌صورت runtime رندر می‌شود.

## توسعه پروژه

- **افزودن پیست:** یک ورودی در `data/resorts.json` (+ آپدیت fallback در `js/resorts.js`) — کافی است. CI تطابق fallback با JSON را بررسی می‌کند.
- **تنظیم فرمول‌ها:** فقط `js/config.js` — همه‌ی وزنه‌ها/آستانه‌ها با مستندسازی.
- **تغییر مدل هواشناسی:** `js/config.js → MODEL.name` (پیش‌فرض `best_match`). مدل‌های دیگر Open-Meteo ممکن است در این منطقه موجود نباشند (`icon_d2` برای ایران پوشش ندارد) — پس از تغییر، گزارش «سلول شبکه‌ی مشترک» را بررسی کنید.
- **رابط تحلیلی:** توابع موتورها pure هستند و ورودی/خروجی ساده دارند؛ جایگزینی هر موتور (مثلاً مدل بهتر سطح برف) بدون لمس بقیه کد ممکن است.
- **AI (اختیاری، آینده):** فقط برای «توضیح بهتر نتایج» — هرگز برای تولید داده هوا یا تصمیم ایمنی.
